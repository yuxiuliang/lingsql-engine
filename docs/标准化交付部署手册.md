# LingSQL 标准化交付部署手册（Docker）

> 版本：v1.0  
> 更新日期：2026-08-15
> 适用对象：实施工程师、SRE、售前技术

---

## 1. 目标

本手册用于快速搭建可演示、可验收、可试点的 LingSQL 标准环境，降低首单交付成本。

---

## 2. 先决条件

- Docker 24+  
- Docker Compose v2  
- 可访问容器镜像仓库（默认 Docker Hub）

---

## 3. 一键拉起（推荐）

1. 准备环境变量文件：

```bash
cp .env.example .env
```

2. 修改 `.env` 中关键参数（必须修改）：

- `MYSQL_ROOT_PASSWORD`
- `MYSQL_APP_USERNAME`
- `MYSQL_APP_PASSWORD`
- `REDIS_PASSWORD`
- `LINGSQL_JWT_SECRET`
- `LINGSQL_DATA_ENCRYPTION_KEY`
- `LINGSQL_ADMIN_PASSWORD`
- `LINGSQL_DEMO_DATABASE`
- `LINGSQL_DEMO_USERNAME`
- `LINGSQL_DEMO_PASSWORD`

3. 执行一键拉起：

```bash
./scripts/ops/bootstrap_local_stack.sh
```

脚本会自动完成以下动作：

- 启动 MySQL 与 Redis 容器
- 由初始化脚本创建应用账号，先撤销历史权限，再仅授予 `SELECT/INSERT/UPDATE/DELETE`；演示账号仅授予 `SELECT`
- 查询 `information_schema.SCHEMA_PRIVILEGES` 失败关闭校验，权限超出或缺失都会终止启动
- 运行短生命周期 Flyway 迁移任务；DDL 使用 root，应用账号不获得 DDL 权限
- 对空库执行冻结合并基线；对未纳管现有库先做完整结构指纹校验再显式 baseline
- 导入 `sql/seed_commercial_baseline.sql` 商业化基线套餐
- 初始化虚构的销售库存演示库
- 启动应用并等待 readiness 健康检查通过

---

## 4. 手动分步部署

若需要分步排障，可按以下命令执行：

手工直接执行 Compose 不会创建应用账号；必须至少运行一次初始化脚本。推荐用 `SKIP_APP_START=true` 完成数据库结构、账号权限和演示库初始化，再启动应用：

```bash
SKIP_APP_START=true bash scripts/ops/bootstrap_local_stack.sh
docker compose --env-file .env up -d app
```

## 5. 验收检查

### 5.1 首次开户顺序

首次开户必须按以下顺序完成，任何一步未通过都不得把租户标记为“可试用”：

1. 在“租户管理”执行 READY 开户，并一次填写已启用且初始余额为正的套餐、首个租户管理员账号、MySQL 只读数据源、表白名单和字段白名单。系统会在任何控制库写入前执行连接检查并读取 `SHOW GRANTS`；账号包含写入、DDL、授权或角色权限时直接拒绝开户。
2. 系统在同一事务内创建租户、基础权限、租户管理员、套餐余额事实和数据源配置，成功后返回不含密码、JDBC 地址和数据库账号的 READY 回执。不得用普通编辑接口创建或激活缺少任一前置条件的半成品租户。
3. READY 回执只证明登录、计费和数据源前置事实已提交，不等于首问已经验收。开户后必须同步 Schema，并确认表数量与客户批准的白名单一致；后续更新数据源会重置 Schema 状态并在事务提交后关闭旧连接池、清理旧缓存。
   数据源更新、停用租户重新启用、续期并激活或启用状态下切换套餐时，系统会重新核验套餐、余额、管理员、基础权限及白名单表真实只读访问；不得通过普通编辑绕过 READY 门禁。
4. 新增或修改模型配置后，系统会强制停用并重置为“待验证”。点击“验证”实际调用 `/v1/chat/completions`，验证通过后再由管理员显式启用；健康页出现“未验证”或“验证失败”时不得进入真实问数验收。
5. 在“模型管理 → 租户授权”选择业务租户并保存完整模型路由；该页面对应 `PUT /api/v1/admin/tenant-model-routes/{tenantId}`。只能选择已启用且验证为 `HEALTHY` 的模型；未授权租户不会回退到全局模型池。升级旧环境时，`V20260816_10` 不会自动授权历史模型，必须由交付负责人依据客户批准的供应商和数据出境边界逐租户配置。
6. “模型管理 → 租户授权”会同步展示首问就绪摘要，其事实来源是 `GET /api/v1/admin/tenant-readiness/{tenantId}/first-question`。确认五项检查全部通过且返回 `status=READY_TO_ASK`、`ready=true`；接口只汇总现有事实，不会自动修复配置，`failureReasons[]` 必须逐项处理后重新查询。
7. 使用新建的租户管理员账号登录，再执行三问和 40 题验收。系统管理员账号不能替代租户账号证明权限边界；运行指纹必须以该业务租户作为 `modelTenantId`，不能使用控制租户的路由指纹替代。

租户管理员初始密码属于一次性交付凭据，应通过约定的安全通道发送并要求客户首次登录后重置；不得写入报告、工单正文、聊天记录或仓库文件。

对于仓库自带的虚构销售库存演示，可在 `.env` 中填写演示管理员和模型参数后执行以下单一入口。它会完成基础设施、演示租户与管理员、白名单数据源、连接验证、Schema 同步、模型真实 Probe/启用、租户模型授权和三问验收；已有资源会按稳定 ID 复核，任何不一致或未验证步骤都会失败关闭：

```bash
bash scripts/ops/bootstrap_demo_pilot.sh
```

若 `.env` 未填写 `LINGSQL_DEMO_MODEL_*`，脚本只复用已经处于 `HEALTHY + active` 的模型；没有可用模型时不会生成假 PASS。重复执行时可设置 `SKIP_INFRA_BOOTSTRAP=true`，但仍会重新验证账号、数据源、Schema、模型和三问闭环。

应用启动后执行：

```bash
curl -fsS http://127.0.0.1:${APP_PORT:-8000}/actuator/health/readiness
bash scripts/ops/schema_drift_guard.sh
bash scripts/ops/flyway_migrate.sh
bash scripts/ops/security_compliance_guard.sh
bash scripts/ops/audit_delivery_guard.sh
docker compose --env-file .env exec -T mysql \
  mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" -e "SHOW GRANTS FOR '${MYSQL_APP_USERNAME}'@'%';"
```

配置试点账号、只读数据源和模型后，必须执行真实业务验收；只通过健康检查不能交付。三问和 40 题脚本都会先调用首问就绪接口，五项检查任一不通过时会在创建计费验收会话和发送业务问题前失败关闭：

```bash
BASE_URL=http://127.0.0.1:${APP_PORT:-8000} \
PILOT_TENANT_ID=<tenant> PILOT_USERNAME=<user> PILOT_PASSWORD=<password> \
PILOT_CONTROL_TOKEN=<dedicated-system-admin-acceptance-token> \
bash scripts/ops/pilot_acceptance.sh
```

手工/UAT 环境不便预先提取短期 Token 时，可用独立控制身份让脚本自行登录；不得回退使用普通试点账号：

```bash
PILOT_CONTROL_TENANT_ID=<system-tenant> \
PILOT_CONTROL_USERNAME=<acceptance-admin> \
PILOT_CONTROL_PASSWORD=<secret> \
bash scripts/ops/pilot_acceptance.sh
```

三条真实问数只证明环境闭环，不能替代客户的 40 题正式验收。双方冻结符合 `docs/schemas/golden-question-suite.schema.json` 的 JSON 后，必须在同一 self-hosted UAT 串行执行 FIRST；有错误题时以不变的 Suite SHA-256 引用首次证据执行 RETEST：

```bash
GQ_SUITE_FILE=./customer-golden-questions.json \
GQ_COMPARATOR_JAR=./dist/lingsql-engine.jar \
GQ_PHASE=FIRST \
GQ_EVIDENCE_PURPOSE=CUSTOMER_UAT \
GQ_OUTPUT_DIR=./reports/customer-gq-first \
BASE_URL=http://127.0.0.1:${APP_PORT:-8000} \
PILOT_TENANT_ID=<tenant> PILOT_USERNAME=<user> PILOT_PASSWORD=<password> \
PILOT_CONTROL_TOKEN=<dedicated-system-admin-acceptance-token> \
bash scripts/ops/golden_question_acceptance.sh
```

自动门禁通过后仍须双方核对冻结 JSON、本机私有商务材料和脱敏报告并签字；未签字不得标记为客户验收通过。FIRST/RETEST 的商务验收记录仅保存在 `.local-private/commercial/`，不得提交远端仓库。

使用虚构数据或内部数据做产品演练时，必须改为 `GQ_EVIDENCE_PURPOSE=INTERNAL_REHEARSAL`。该模式生成的报告会明确标记“内部演练”，不得作为客户验收、合同履约或商用上线证据。

如需完整商用门禁：

```bash
BASE_URL=http://127.0.0.1:${APP_PORT:-8000} \
BILLING_READINESS_URL=http://127.0.0.1:${APP_PORT:-8000}/api/v1/admin/billing/readiness/snapshot \
BILLING_AUTH_HEADER="Authorization: Bearer <token>" \
PILOT_TENANT_ID=<tenant> PILOT_USERNAME=<user> PILOT_PASSWORD=<password> \
PILOT_CONTROL_TOKEN=<dedicated-system-admin-acceptance-token> \
BACKUP_RESTORE_MYSQL_HOST=<uat-mysql-host> \
BACKUP_RESTORE_SOURCE_DB=<control-db> \
BACKUP_RESTORE_TARGET_DB=lingsql_restore_verify_<unique-run-id> \
BACKUP_RESTORE_BACKUP_USER=<backup-user> \
BACKUP_RESTORE_BACKUP_PASSWORD=<backup-password> \
BACKUP_RESTORE_RESTORE_USER=<restore-user> \
BACKUP_RESTORE_RESTORE_PASSWORD=<restore-password> \
BACKUP_RESTORE_BACKUP_DIR=/absolute/protected/backup/path \
BACKUP_RESTORE_WORK_ROOT=/absolute/temporary/path \
BACKUP_RESTORE_SAMPLE_QUERY='SELECT COUNT(*) AS row_count, MIN(id), MAX(id) FROM <stable_business_table>' \
bash scripts/ops/commercial_acceptance_gate.sh
```

GitHub 的严格发布工作流必须配置独立系统租户验收账号的 `RELEASE_GATE_CONTROL_TOKEN`，并映射为运行时 `PILOT_CONTROL_TOKEN`。该账号必须具备 `ADMIN:SQLLOG:READ`、`ADMIN:BILLING:READ` 和系统管理员身份；Token 仅保存于受保护的 UAT Environment Secrets，不得与普通试点账号或 `RELEASE_GATE_BILLING_TOKEN` 共用，也不得把普通试点账号提升为系统管理员。收据封印必须另设 64 位小写十六进制 Secret `RELEASE_GATE_RECEIPT_HMAC_KEY`，不得复用 Bearer Token；独立密钥允许 API Token 轮换而不改变收据验证边界。`PILOT_CONTROL_TENANT_ID/USERNAME/PASSWORD` 只用于受控人工环境的即时登录，不进入 GitHub 工作流或仓库。受保护 Environment 还必须同时设置 `RELEASE_GATE_GQ_SUITE_FILE` 与 `RELEASE_GATE_GQ_SUITE_SHA256`：前者指向 self-hosted runner 上已冻结、权限受控且不会提交到仓库的 40 题 Suite，后者保存双方预授权的 64 位小写 SHA-256。Runner 会先核验哈希，再复制为权限 `600` 的一次性快照并执行，避免同一路径在验收过程中被替换。严格发布和候选切流均以 `FIRST` 模式执行该 Suite，任一指标不通过均不得放行；`RETEST` 还必须提供首次证据文件及其预授权 SHA-256，且首次证据必须是一题一条、40 题唯一、批量审计计费证据完整的 `FIRST` 记录。

目标环境还必须显式设置 `LINGSQL_RUNTIME_DATA_SNAPSHOT_ID`，标识本次验收使用的不可歧义数据快照。正式 JAR 构建写入 Git SHA；运行指纹接口只对系统管理员开放，并要求 `modelTenantId`，返回 Git SHA、Flyway 最新成功版本、数据快照 ID 和该租户授权模型路由 SHA-256。发布环境将 `MODEL_ROUTE_TENANT_ID` 设置为真实试点租户，控制账号租户仅用于鉴权。发布工作流先完成迁移兼容性扫描、控制库真实备份恢复和旧版本迁移后冒烟，随后才把候选启动在非活跃槽位。候选门禁命中候选端口核对运行指纹；40 题结束后和生成候选收据前都会再次核对，不得把部署前旧实例的绿灯复用为候选版本证据。

每个蓝绿槽位还必须独立消费 `${LINGSQL_DEPLOY_BASE}/<slot>/runtime.env`。发布脚本会以原子替换方式生成只读文件，只包含 `LINGSQL_RUNTIME_BUILD_COMMIT`、`LINGSQL_RUNTIME_SLOT` 和 `LINGSQL_RUNTIME_RELEASE_ID` 三项非敏感身份。systemd 服务必须分别声明精确路径，例如蓝槽位使用 `EnvironmentFile=/opt/lingsql/blue/runtime.env`、绿槽位使用 `EnvironmentFile=/opt/lingsql/green/runtime.env`；脚本会读取 unit 的 `EnvironmentFiles`，未消费对应文件时直接拒绝启动。非 systemd 启动模板必须包含 `{runtime_env}`，并在启动 Java 前导入，例如 `set -a; source {runtime_env}; set +a; exec java -jar {artifact} --server.port={port}`。禁止通过全局 `systemctl set-environment` 注入，避免并行发布的槽位身份相互污染。

严格发布同时生成两类不能混用的 SLO 证据：迁移前的 `historical_service_slo.md` 反映在线服务滚动 30 天历史；候选启动后对其隔离端口执行 200 次已认证的 `GET /api/v1/admin/runtime/fingerprint?modelTenantId={pilotTenantId}`，覆盖认证、控制库/Flyway 和试点租户模型路由指纹读取，再生成 `candidate_slo.md`。候选 PromQL 强制按本次 `build_commit`、`slot`、`release_id` 过滤并逐项核对 Prometheus 实际返回标签，禁止自定义查询移除过滤。Prometheus 必须直接抓取两个槽位的独立端口，不能只抓取切流后的统一域名。受控负载使用 `RELEASE_GATE_CONTROL_TOKEN` 和 `RELEASE_GATE_CONTROL_TENANT_ID`，模型路由范围使用独立的 `MODEL_ROUTE_TENANT_ID`；Token 只经权限 `600` 的临时 curl 配置传递，不进入报告或子进程参数。候选收据绑定 `candidate_slo.md` 的 SHA-256，历史服务 SLO 只作为发布前全局健康门禁，不能替代候选证据。

### 5.2 迁移前保护与 Hook 收据

严格发布必须设置 `RELEASE_GATE_CONTROL_DB` 和独立的 `RELEASE_GATE_CONTROL_DB_SAMPLE_QUERY`。后者只能读取控制库真实稳定表，首列返回正整数；它与客户业务库的 `RELEASE_GATE_BACKUP_SAMPLE_QUERY` 是两个不同证据。工作流按以下顺序失败关闭：

1. `migration_compatibility_guard.sh` 读取控制库 `flyway_schema_history`，只扫描版本高于当前版本的 `V*.sql`；无法仅按版本判定 pending 状态的 `R__*.sql` 在标准自动发布中直接拒绝。自动发布只接受新增表、索引和可证明兼容的纯 `ADD` 变更；`DROP`、`RENAME`、`CHANGE`、`MODIFY`、`ALTER COLUMN`、无默认值的非空新列、数据改写及无法安全解析的语句全部拒绝。需要破坏性迁移时必须退出标准自动发布，另行走维护窗口和人工变更审批。
2. `backup_restore_acceptance.sh` 在迁移前对控制库创建真实备份，校验 SHA-256，恢复到全新隔离数据库并比较结构与样例指纹。只有报告为 `PASS` 才能调用迁移 Hook。
3. `migration_release_guard.sh` 在 Hook 前记录当前在线提交和 Flyway 版本，向 Hook 传入独立证据环境变量及唯一收据草稿路径。Hook 完成后，守卫独立查询实际 Flyway 版本、校验收据，再对仍在线的旧提交执行完整发布冒烟和运行指纹复核；旧版本不兼容迁移后结构时，不会启动候选。
4. 守卫将通过复核的 Hook 草稿规范化，并以硬链接发布为权限 `400` 的不可覆盖 JSON 收据。最终收据及旧版本兼容性报告会进入候选 HMAC 收据和 self-hosted 本地证据归档。

迁移 Hook 的调用参数依次为目标 Git SHA、发布标签、收据草稿路径；环境变量 `MIGRATION_HOOK_RECEIPT_FILE` 也指向同一路径。Hook 必须在迁移成功后自行生成以下 JSON，禁止复用旧文件或仅打印到日志：

```json
{
  "schemaVersion": 1,
  "createdAt": "2026-08-15T10:00:00Z",
  "releaseCommit": "40位小写GitSHA",
  "releaseTag": "v2026.08.15.1",
  "preMigrationVersion": "20260815.07",
  "postMigrationVersion": "20260816.01",
  "pendingMigrationChecksumSha256": "64位小写SHA-256",
  "compatibilityReportSha256": "64位小写SHA-256",
  "backupSha256": "64位小写SHA-256",
  "backupRestoreConclusion": "PASS",
  "hookConclusion": "PASS"
}
```

Hook 应直接复用守卫注入的 `MIGRATION_PRE_VERSION`、`MIGRATION_EXPECTED_POST_VERSION`、`MIGRATION_PENDING_CHECKSUM_SHA256`、`MIGRATION_COMPATIBILITY_REPORT_SHA256`、`MIGRATION_BACKUP_SHA256` 和 `MIGRATION_BACKUP_RESTORE_CONCLUSION`；不得自行猜测或跳过字段。守卫会将这些值与数据库和前置报告逐项复核。

候选门禁全部通过后，`release_candidate_receipt.sh create` 会在部署目录的 `run/candidate_acceptance_receipt.json` 生成一次性 JSON 收据。收据绑定候选 Git commit、槽位、端口、发布 ID、槽位 `app.jar` SHA-256、规范化运行指纹 SHA-256、迁移 Hook 收据 SHA-256、冻结 40 题 Suite SHA-256、逐题 evidence SHA-256，以及旧版本迁移兼容性、运行指纹、40 题、三问、灾备、商用总门禁和 SLO 报告 SHA-256。收据使用独立 `CANDIDATE_RECEIPT_HMAC_KEY` 对规范化 JSON 计算 HMAC-SHA256 封印；Node.js 从环境读取密钥和标准输入中的规范化 JSON，密钥不会写入收据、命令参数或命令输出。创建采用权限 `400` 的不可覆盖硬链接语义，残留同名收据会使发布失败，禁止人工删除后绕过调查。

逐题 `evidence.jsonl` 包含请求、逐题和计费审计明细，禁止作为 GitHub Actions Artifact 上传；运行指纹、三问和灾备报告同样不得上传远端。切流前，逐题证据及 40 题、运行指纹、三问、灾备、商用、SLO、迁移 Hook 收据和旧版本兼容性报告会以固定文件名复制到 self-hosted 部署机 `${LINGSQL_DEPLOY_BASE}/evidence/<release-id>/`：目录权限 `700`、文件权限 `400`、目标存在时只接受摘要完全相同的幂等重试，绝不覆盖。远端工作流制品只保留脱敏汇总报告与不含凭据的迁移技术证据。

切流必须同时提供工作流期望的 `EXPECTED_RELEASE_COMMIT`、专用 `PILOT_CONTROL_TOKEN` 和独立收据 HMAC 密钥。`release_candidate_promote.sh` 会在切流前重新计算当前槽位 `app.jar` 与所有验收文件摘要、验证收据封印，并直接访问候选端口复核运行 Git commit；任一内容变化都会失败关闭。永久归档 `receipts/<release-id>.json` 和本地证据会在切流前以不可覆盖方式预留，归档冲突发生在切流之前；切流成功后只移除指向同一 inode 的运行中收据。门禁后中止也保留同一永久归档，最终发布或中止结果以 `release_history.log` 中追加的状态记录区分。收据证明指定制品通过了本次技术门禁，但不替代客户签字、合同或到账证据。

### 5.3 备份恢复抽查

`RELEASE_GATE_BACKUP_SAMPLE_QUERY` 必须是针对真实业务表的确定性只读聚合查询，第一列必须返回正整数业务行数；禁止 `SELECT 1`、无 `FROM` 的纯常量查询和 `information_schema` 查询。其余列可返回稳定的主键范围、金额汇总或脱敏摘要。门禁会同时比较源库备份窗口前后与隔离恢复库的完整输出 SHA-256，确保不是只恢复了空结构。

商用总门禁会调用 `scripts/ops/backup_restore_acceptance.sh`。该脚本复用 `mysql_backup.sh` 与 `mysql_restore.sh`，执行以下不可跳过检查：

1. 使用只读备份账号对 UAT 控制库创建本次真实备份并验证 SHA-256。
2. 备份前后分别计算结构与客户配置的只读样例数据指纹；源库在备份窗口发生变化时失败，避免用不稳定快照出具证明。
3. 只允许恢复到运行前不存在的 `lingsql_restore_verify_` 前缀数据库，禁止指向源库或覆盖已有数据库。
4. 恢复后重新计算结构和样例指纹并逐项比对。
5. 退出时只清理固定验证前缀数据库和受控绝对临时目录；真实备份保留在受保护绝对路径，报告只记录不可逆摘要。

备份账号应只有读取、`LOCK TABLES`、视图/触发器/事件导出所需权限；恢复账号只能在隔离 UAT 实例创建和删除验证前缀数据库，不得连接生产 MySQL。样例查询必须是一条无分号 `SELECT`，返回稳定的计数/聚合结果，且不得输出客户明细。self-hosted Runner 必须安装 `mysql`、`mysqldump`、`gzip` 与 `sha256sum`。

严格工作流的 Environment Variables：

- `RELEASE_GATE_CONTROL_TENANT_ID`
- `RELEASE_GATE_MYSQL_HOST`、`RELEASE_GATE_MYSQL_PORT`
- `RELEASE_GATE_CONTROL_DB`（Flyway 控制库；迁移前单独备份恢复）
- `RELEASE_GATE_BACKUP_SOURCE_DB`、`RELEASE_GATE_BACKUP_DIR`（self-hosted Runner 上的受保护绝对路径）
- `RELEASE_GATE_BACKUP_USER`、`RELEASE_GATE_RESTORE_USER`

严格工作流的 Environment Secrets：

- `RELEASE_GATE_BACKUP_PASSWORD`、`RELEASE_GATE_RESTORE_PASSWORD`
- `RELEASE_GATE_CONTROL_DB_SAMPLE_QUERY`、`RELEASE_GATE_BACKUP_SAMPLE_QUERY`

## 7. 生产建议

- 使用外部托管 MySQL/Redis，并开启备份与高可用。
- Compose 默认仅把 MySQL、Redis 和应用端口绑定到 `127.0.0.1`；只有经防火墙、TLS 网关和访问控制评审后才可修改 `*_BIND_ADDRESS`。
- 应用容器使用非 root UID、只读根文件系统、`no-new-privileges` 并移除 Linux capabilities；客户环境不得删除这些约束来规避权限问题。
- `LINGSQL_RETENTION_DRY_RUN` 先保持 `true`，观察 7 天后再关闭。
- 通过网关/Nginx 统一接入 HTTPS，限制管理端来源 IP。
- 将 `.env` 纳入密钥管理系统，不在仓库中明文保存。
- 生产发布由严格工作流强制先扫描 pending 迁移、完成控制库真实备份恢复，再由 `LINGSQL_MIGRATION_HOOK` 执行 Flyway；缺少不可覆盖收据或迁移后旧版本冒烟失败时禁止启动候选。应用制品回滚不会自动回滚数据库。
- 所有新迁移必须向前兼容上一稳定应用版本。MySQL 多条 DDL 不具备整体事务回滚能力，失败后禁止未经核验直接 `repair`。
